# 발표 대본
## Wazuh 보안 정책 구성 및 자동화

---
[슬라이드 1 / 담당한 부분 소개 — 약 10초]  
저는 구축된 환경 위에서 Wazuh를 이용해 자동화된 보안 관제 체계를 구성했고,  
그 내용을 바탕으로 인프라 설정 시 주의해야 하는 점들을 뽑아 보안 가이드를 작성했습니다.

---
[슬라이드 2 / 구성 방향 — 약 40초]  
Agent가 설치된 서버는 총 10대입니다.  
이때 각 서버에 직접 접속해서 ossec.conf 파일에 로그 수집 정책을 수동으로 작성하면, 서버마다 정책이 달라지거나 누락이 생길 수 있어 해당 서버가 공격의 시작점이 될 수 있습니다.  

그래서 siem-01 서버 한 곳에서 SSH로 전체 10대에 접속할 수 있도록 일괄 배포하는 쉘 스크립트를 만들었습니다.  
또 이 사진은 06-wazuh_all.sh 스크립트를 실행한 결과입니다.  
Agent 등록, pfSense 연동, 로그 수집(Agent & pfSense), Indexer 저장, Active Response 설정까지 5단계를 한 번에 실행할 수 있게 구성했습니다.  

---
[슬라이드 3 / 데이터 흐름 — 약 40초]  
데이터 흐름은 이렇습니다.  
10대 서버의 Wazuh Agent가 로그(SSH 인증, 시스템, FIM(파일 무결성 감시) / Kubernetes 한정 컨테이너, API 감사)를 수집하면,  
1514번 포트를 통해 TCP 통신으로 Manager에 전송하게 되는데, 이때 Manager가 룰로 분석해 JSON 경고문을 생성합니다.  

그러면 Filebeat가 이걸 읽어 Indexer(OpenSearch)에 저장하고, 대시보드에서 확인할 수 있습니다.  
이때 Wazuh Dashboard와 Grafana를 연동해 한 화면(Grafana)에서 확인할 수 있도록 구성했습니다.  

---
[슬라이드 4 / 설계 포인트 1 — pfSense Agentless — 약 30초]  
pfSense는 네트워크 최전방 방화벽 장비입니다. 여기에 Agent를 설치했다가 안정성 문제가 생기면 전체 네트워크 장애로 이어질 수 있습니다.  

그래서 Agent 대신 514번 포트를 통해 UDP 통신으로 Syslog를 Manager에 직접 전송하도록 구성했습니다.  
방화벽이 뚫리는 상황이 오더라도 내부 10대 Agent가 계속 동작하기 때문에 위협은 계속해서 탐지할 수 있게 됩니다.  

---
[슬라이드 5 / 설계 포인트 2 — Active Response — 약 40초]  
Brute Force(무차별 대입) 공격은 짧은 시간에 수천 번 반복되기 때문에 관리자가 수동으로 대응하면 이미 늦을 수 있습니다.  
저희 인프라에서 Kubernetes는 클러스터로 묶여있는 구조이기 때문에 SSH 한 곳이 뚫리면 클러스터 전체로 공격이 확산될 위험이 있습니다.  

그래서 SSH 관련 2가지, pfSense 관련 2가지, 총 4개의 차단 정책을 Active Response로 설정했습니다.  
SSH Brute Force와 인증 반복 실패가 탐지되면 해당 서버에서 즉시 공격 IP를 차단하도록 구성했습니다.  
pfSense에서도 포트스캔이나 OpenVPN 브루트포스가 탐지되면 내부망 전체를 노리는 공격이므로 전체 10대 서버에서 차단하도록 구성했습니다.  

---
[슬라이드 6 / 보안 가이드 — 약 50초]  
탐지와 차단만으로는 부족합니다. 애초에 취약한 설정으로 서버가 운영되고 있다면 공격이 들어오기 전에 이미 위험한 상태이기 때문입니다.  

그래서 Wazuh 로그를 포함해서 Docker, Kubernetes, Linux Host OS 환경에 대한 보안 가이드를 작성했습니다.  
가이드는 항목별로 왜 위험한지, 어떻게 진단하는지에 관한 내용이 들어있습니다.  

이렇게 Wazuh 서버가 실시간으로 탐지하고, 자동으로 차단하고,  
보안 가이드의 점검 기준을 통해 사전에 예방할 수 있도록 구성해 두 체계가 서로 보완되도록 만들었습니다.  

이상입니다. 감사합니다.
